# 项目滚动推进

让用户主要做选择或说“继续推进”，不要求反复提供长提示词。把已批准目标变成可执行模块，以 PLAN → DO → CHECK → ACT 循环推进；磁盘上的事实与证据是进度依据，聊天不是唯一记忆。

## 入口与恢复

1. 先检查当前工作目录及适用 AGENTS.md。查找 `project-control/progress.json`；不要递归寻找或打开别的项目。若不存在，先盘点现有代码、文档和用户需求，再建立进度档案并提出首个范围选择，不能凭产品策划文档假设所有设计已获批准。
2. 执行本 Skill 的 `scripts/progress.py show --root <项目根>` 和 `validate`。读取 `project-control/HANDOFF.md`，若存在 `project-control/PRODUCT_UX_PRINCIPLES.md`，恢复时一并读取；若项目存在 `project-control/ROADMAP.md` 与模块 `prd_ref`，一并核对路线和当前PRD；然后只加载当前模块 plan、最近证据、相关决策与必要源码。新对话必须直接读取这些文件，不要求用户重讲历史。
3. 将进度与实际文件、代码差异、测试证据核对。路径缺失、文件变化、未完成写入或并发冲突时先修复记录；涉及正确性的状态降级为 needs_recheck。不要把“代码存在”“测试命令已写出”当作测试通过。
4. 用户指令路由：
   - **继续推进 / 接着做**：执行已批准范围内的下一项可执行工作，直到一个实质检查点、关键决策、运行权限需求、外部阻碍或合理单轮结束；不是无条件批准待决策事项。
   - **选择A / 采用推荐方案**：只有能够唯一对应当前显示的 decision_id 及选项时才登记用户选择；否则只问一个定位问题。
   - **查看进度**：只读汇报当前模块、证据、阻碍及下一步。
   - **变更 / 回退 / 暂停**：先保存状态；变更执行影响分析，暂停只在用户要求时使用。
   - **新对话续接**：读取档案恢复。不得重置 progress 或重新初始化现有代码。
5. 当前存在未回答的阻断决策时，不越过它实现相关方案。可以做不预设选项的低成本调查或证据整理。已有失败若存在有价值的排查路径就继续排查，不无限重复同一命令。

进度格式和可靠更新方法见 [references/state-contract.md](references/state-contract.md)。需要更换状态字段或修改脚本时才阅读全文。

## 模块 PDCA 循环

只详细规划当前模块与紧邻依赖，远期模块保留目标、依赖及风险，避免一次生成几十份无用文档。每模块使用 `project-control/modules/<id>/plan.md`，测试与审计保存在 `evidence/`，路径在 progress 中登记。用户要求模块PRD时，维护独立需求→来源→验收追踪，不把未来PRD当已批准详细PLAN或已实现证据。

### PLAN 规划与选择

读取 [references/delivery-cycle.md](references/delivery-cycle.md) 的 PLAN 和当前模块测试条目。盘点已获批准的共享技术栈，默认复用；当前模块给出目标、非目标、输入输出契约、依赖、实现步骤、验收标准、测试、风险与回滚方式。技术选型比较一个推荐方案和至多两个有实质区别的替代方案，说明许可证、维护成本、部署及兼容性。版本须核对真实运行环境；无法联网查证时标为待验证。

在会产生长期或高成本影响的关键点展示 decision_id、推荐选项、替代项、取舍及建议。用当前可用且适用于此模式的选择工具；否则用一个清晰的短问题征询，避免连续提问。首次立项可让用户一次选择相互一致的方案包。plan 获用户确认后将该决策写入 progress.decisions，才进入 DO。已批准共享栈的机械沿用、低风险修复和测试细节不重复要求批准。

### DO 功能实现

按批准计划实施一个可演示、可测试的最小垂直切片，维护接口及迁移。优先真实端到端链路，mock 仅服务隔离测试与UI开发，不冒充真实MCP或数仓集成。每项完成附可验证路径或结果；安全和架构约束用代码实施，不能只写提示词。遇到范围扩大、契约破坏或栈变更先停相关工作进入新决策。

不要创建新聊天或启用子 Agent 作为默认手段。只有用户、适用仓库指令明确授权委派时才使用子 Agent；有授权时拆分独立写入范围、明确结果与集成检查。此 Skill 自身不授予任何外部访问、生产执行、安装、推送、发布或文件删除权限。

### CHECK 功能与集成测试

执行当前切片的单元、契约、集成及所需端到端测试，追加安全、UI或统计方法专项检查。报告运行命令、实际退出结果、测试环境、代码指纹、覆盖场景、失败及未运行项。问题先修复，再复跑受影响检查；不得通过删除断言、全局跳过或无理由放宽容差让结果变绿。

没有凭证或真实服务时，mock 测试可以通过，但真实集成必须写 not_run；此时只能提供有限的 local_ready 结论，不能标 production_verified、closed 或称已连通真实数仓。用户可批准“真实验证延期”的交付范围调整；需要登记依赖、责任人和补验条件，保留正式发布门禁。密钥只能由用户在安全渠道配置，不写入进度、Prompt或日志。

### ACT 交付审计与改进

审计需求覆盖、真实测试证据、输入输出合同、权限、错误分支、数据来源、部署运行、回滚和未解决风险。使用同一主 Agent 审计时注明 self_review，不称独立审计。无必须阻断问题才为当前已约定交付范围标 audit pass；真实环境延期验证仍列在项目发布门禁内。重大残留问题不能因用户说“继续”自动忽略。

给用户短验收摘要和实际可检查结果，提出 delivery 决策。用户明确验收或事先授权的低风险批量验收规则满足后，才 closed 并进入下一模块 PLAN。提前批量授权必须记录适用范围、排除项与检查标准；新栈、数据权限、生产部署、重大方法和破坏性变更仍须单独确认。未验收前可以准备下一模块的低风险调查，但不擅自更换 active_module。

CHECK/ACT 失败 → DO 修复 → 重跑 CHECK → 再审计；需改变方案 → 新一轮 PLAN 并新建 cycle_id。记录简短根因、改进与影响，不为每一次微小修复生成长报告。具体门禁见 [references/delivery-cycle.md](references/delivery-cycle.md)。

## 产品用户思维门禁

本Skill不仅推进代码，还要推进可用产品。每模块PLAN及ACT都读取 [references/product-user-thinking.md](references/product-user-thinking.md)；项目有PRODUCT_UX_PRINCIPLES.md时以其中已确认的用户目标及交互约束补充，不把某个项目的深色配色或聊天布局强加到其他项目。

- PLAN先确定谁在什么情境完成什么任务、为何需要这个模块，再选技术栈。给出最短默认路径、角色分层、关键状态及一项可观察的任务成功标准。对不能解释用户价值的模块，建议隐藏、延期或缩小，不机械堆功能。
- DO采用渐进披露：业务结论与可操作结果优先，口径/来源/质量可查，SQL/Schema/工具日志默认折叠给专业用户。不得把工程验证器变成业务首页；管理员接入流程不要求普通业务用户配置数仓或填写JSON。
- CHECK除了接口通过，还应走一遍真实用户路径：入口是否能发现、文案是否能理解、是否有有效下一步；主题选项应有可见文字和选中态，不能只用隐蔽图标。正常、加载、空、拒绝、失败、部分结果及恢复按风险覆盖。
- ACT记录用户任务→实现→证据，区分功能测试、走查和真实用户研究。不能把开发者自测宣称为真实用户验证或已验证市场需求。应聘作品可以记录决策理由和未验证假设，不编造访谈、留存或业务收益。
- 请求处理状态与已确认能力一致，不通过动画模拟找表/SQL成功；未接入、规则提示、mock、结构校验和真实Agent输出明确区分。不同颜色的来源标签不是质量评级或因果证明。
- 改动产品交互后同步项目原则与影响记录，重新跑相关用户路径。用户已确认的默认路径、明确主题入口及证据层级不得被后续模块无理由撤回。新增权限、数据驻留或重大流程取舍才请求决策，低风险布局修复不反复打断。

## 本项目的产品架构约束

当项目是通用企业智能数据分析平台时，使用 [references/data-platform-roadmap.md](references/data-platform-roadmap.md) 规划模块；它是待用户确认的推荐路线，不是强制技术栈。

- 取数 Agent 必须通过 MCP 或其受治理适配层获得授权内真实元数据、生成合法SQL、提交 Spark/Hive 等执行服务并取回结果。指标引擎是优先路径，不替代数仓访问。
- MCP 元数据接口与执行接口可来自不同服务。不能把“MCP存在”当作方言、取消、行列权限等能力均兼容。
- 数据资产契约发生在取数后的交接层，不取消数仓连接。下游读授权资产；新增数据需求回到取数主干，用户明确批准的独立数据输入除外。
- 继承 L1/L2/L3 路由、L4 明确目标入口、关键口径澄清、SQL及Python质检、权限拒绝不绕路；安全由服务端落实。来源色标与质量状态分离。
- 归因、建模与实验需要方法与数据条件检查。贡献、相关性和因果识别不可混称。

## 本项目的模型服务优先级（条件适用）

仅当项目档案确认 `project.id=universal-data-agent` 且有 D-ROADMAP-MODEL-014 时，读项目 `project-control/ROADMAP.md`、PRD入口与当前 `prd_ref`：采用 **M02 收尾 → M04-A 模型 API 接入 → M03 语义知识库 → M04-B LangGraph 编排的受控问数**。保留旧进度ID M04作为M04-B，新M04-A单独验收；模型服务与数据源连接器分开。其他项目以其自己的批准路线为准。

M04-A先薄ModelProvider适配，M04-B优先LangGraph图编排；方向批准不等于具体版本/安装/模型费用/端点/数据外发批准。框架不能替代已有MCP、Worker、服务端SQL/权限或幂等回执，不默认外部追踪。详细边界见 [references/data-platform-roadmap.md](references/data-platform-roadmap.md)。原M02待清理决策和真实验证门禁不得被新路线自动绕过。

## 进度与每轮收尾

任何关键选择、实现切片、测试结果、阻碍和阶段变化后都 checkpoint；较长任务中每完成一个可复现步骤写一次，不等上下文耗尽。使用工具生成 `progress.draft.json`，调用 `progress.py checkpoint --root <root> --draft <draft> --expected-revision <旧revision>`。脚本生成 HANDOFF 并校验 revision、决策及证据，不能凭脚本通过代替审计。不要直接覆盖主进度；证据用唯一文件名以便保留历史。状态和备份不存令牌、敏感样例或大段工具输出。

停止前确保进度包含：当前模块及阶段、已完成及未完成项、审批、实际测试、残留风险、准确 next_action、所需文件、复现命令、工作树差异和新对话建议。意外中断时，下一轮从代码和证据恢复；若HANDOFF落后，以经校验的progress为准。

每轮回复不超过必要篇幅，默认结构：本轮完成、验证结果、当前进度、下一步；只有确有关键选择时附选择卡。不要捏造精确总体完成百分比，优先给出模块数量及当前阶段。无待决策且还有可执行工作时用户可直接说“继续推进”。

## 新对话建议与交接

满足任一条件时建议在检查点切换：一个模块已审计并验收；接下来切换到新的专业模块；当前上下文装入大量源码或日志导致早期约束容易丢失；发生较大范围变更；长周期运行已完成且要进入新决策。没有可靠上下文计数时仅作定性判断，不编造剩余token或阈值。不为了换窗口中断正在进行且不易恢复的迁移或运行。

推荐而不自动创建或切换聊天。先保存checkpoint，再给一句交接指令：

> 在同一项目目录使用 $project-pdca，读取 project-control/progress.json 和 HANDOFF.md，核对实际文件后继续推进；遵守已登记决策，不重建项目。

若用户明确要求创建新聊天，再使用本轮可用的聊天工具，并仅传项目位置、续接指令和必要状态引用。新聊天是否自动发现Skill、是否有MCP及凭证必须以实际环境确认；已安装Skill不保证旧会话立即刷新。不得声称仅说“继续推进”就能让一个完全未关联项目的新聊天找到记录。
